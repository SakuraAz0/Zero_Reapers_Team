# 纪念 · CRTC_ZRTeam_ROBORT1 开发全记录

> 一辆车、两次封版、若干次凌晨调参，和比赛结束之后写下的一篇纪念。
>
> 这里写的不只是"怎么写的代码"，还有"为什么这么写"、当时卡在哪里、最后是怎么出来的。
> 有些地方已经记不清具体时刻了，就按工程仓库里的时间戳和提交记录补上。

## 0. 写在前面

这个项目从一块 STM32F103C8T6（俗称 Blue Pill）开始，最后变成一辆能跑麦轮、能伸机械臂、
能一键完成"放下/摆臂"、能用手柄带 2.4G 无线操作的比赛车。

中间换过一次车：第一辆车（下称**车1**，4 个舵机）在 10 月 30 日封版，打上 `car1-finished` 标签；
第二辆车（下称**车2**，3 个舵机、结构重新设计）在 10 月 31 日完成最后一轮调参。

比赛结束之后回头整理，发现真正难的不是"写出能动的代码"，而是：

- 让它在**每一次**都动得一样（标定、限位、曲线、软启动）；
- 让**操作手**不用去记复杂的组合键（一键动作、模式划分）；
- 让**别人**（未来的我们）打开仓库就能看懂（宏、注释、文档、回归测试）。

这篇文章就是这三件事的记忆。

## 1. 缘起：一块 Blue Pill

一开始只是一块常用开发板：72MHz 的 Cortex-M3、64KB Flash、20KB RAM。
外设规划得很朴素：

| 用途 | 外设 | 备注 |
|---|---|---|
| 底盘 PWM ×4 | TIM2 / TIM4，各 2 通道，1kHz | 占空比 0~1000 |
| 舵机 PWM ×4 | TIM3 CH1~CH4，50Hz，1µs 分辨率 | 500~2500µs 安全窗口 |
| PS2 手柄（2.4G 接收器） | GPIOB PB12~PB15，软件时序 | DI/DO/CS/CLK，不占用 SPI 硬件 |
| 调试 LED | GPIO | 复位原因闪码、档位指示 |

软件栈是 **CubeMX 生成 + CMake/Ninja + CLion**，工具链用 STM32CubeCLT 自带的
`arm-none-eabi-gcc`。选择 CMake 而不是 CubeIDE 的原因很简单：想用 CLion 的补全和重构，
也想让构建过程能被脚本（`tools/flash.ps1`）一键复现。

第一版代码写得很快，但很快发现：**能跑**和**能用**之间隔着一整个赛季。

|---|---|---|
| 主控 | STM32F103C8T6 | 最小系统板 |
| 底盘电机 | 直流减速电机 ×4 | 麦克纳姆轮，斜 45° 安装 |

## 3. 软件地基：三层循环

整个程序其实是三层，从慢到快：

```
┌─ 主循环（每 10ms 一个 tick）─────────────────────────────┐
│  1) 读 PS2（一整包 9 字节，同 CS 窗口内收发）            │
│  2) Ctrl_Update()  → 摇杆/按键 → vx, vy, vw（底盘意图）  │
│  3) Servo_Task()   → 机械臂/机械爪（含序列状态机）       │
│  4) Mecanum_MoveLimitSlew() → 逆解 + 软启动 → PWM        │
└──────────────────────────────────────────────────────────┘
        ↑ 所有动作都是"状态机 + 斜坡"，没有一处 HAL_Delay 阻塞
```

**关键原则：主循环里绝不阻塞。** 舵机插值、一键序列的"等上一步到位"、软启动、看门狗喂狗，
全部拆成每 tick 推进一点的状态机。这条原则在后面救了很多次：
只要主循环还在转，手柄就有响应，看门狗就不会咬。

节拍最初是 10ms。后来为了"更跟手"，我们把 `PS2_READ_PERIOD_MS` 提到 **5ms（200Hz）**，
顺便把舵机节拍 `SERVO_TICK_MS` 和马达软启动步长一起联动改掉——
这个决定在几天后引发了一场"手柄为什么总掉模式"的战争（见第 6 节），最后又老老实实改回 10ms。

## 4. 车1：从"能动"到"敢上赛场"

### 4.1 PS2 驱动的第一次重写：0x5A 的误会

最早的手柄读取一直"偶尔丢包、偶尔全 0"。翻参考实现、示波器看时序，最后定位到一个很傻的 bug：

- 参考代码里那句 `PS2data[1] != 0x5A` 被当成"连接是否正常"的判断；
- 但 **0x5A 是响应包的第 3 个字节（buf[2]）**，是"数据就绪"标记；
- 拿 buf[1]（模式/型号 ID）去和 0x5A 比，永远不相等 → 只要手柄正常，代码反而认为它异常。

于是整包重写：同一个 CS 窗口内发 9 字节、收 9 字节，包间隔 1ms，
按键低/高字节顺序按 `(buf[4]<<8)|buf[3]`，摇杆四轴取 buf[5..8]。
**这次教训写进了 `docs/PS2-诊断与修复方案.md`（40KB 的那份长文档）**——
那大概是整个项目写得最认真的一份排障笔记。

### 4.2 复位之谜：闪码与电源

上电跑一会儿就复位、或者一推电机就复位。为了定位，加了"用 LED 闪码报告复位原因"：

| 闪数 | 原因 |
|---|---|
| 2 | PIN 复位 / 上电复位（POR） |
| 4 | 软件复位 |
| 6 | IWDG 看门狗复位 |

排到最后发现**不是代码问题，是电源问题**：电机瞬间电流把 5V 拉下去，
MCU 掉压复位；还有一次是接线端子松动。解决办法是加粗电源线、加储能电容、STBY 直连 VCC，
并且烧录用 **ST-LINK hot-plug 模式**（因为板上没有接 NRST 线，
"先复位再连接"会因 IWDG 正在计数而失败）。

> 这段经历之后，我们养成了一个习惯：**先怀疑电源，再怀疑代码。**

### 4.3 机械臂：从 0.1° 的执念开始

车1 有 4 个舵机：MG995（大臂）、SG90 下、SG90 上、MG90S（机械爪）。
舵机控制的核心是两条换算：

```
脉宽(µs) = 500 + 电气角(°) × 1000/90
电气角   = 机械角 − 零点偏移(OFFSET_DEG)
```

每路只允许手填 4 个宏（`OFFSET` / `MIN_ANGLE` / `MAX_ANGLE` / `START_ANGLE`），
`MIN_US/MAX_US/START_US` 全部自动算出来，并在编译期用 `#warning` 自检是否撞到 500/2500µs 的硬边界。

这样做的代价是——**每次现场都要重新标定一遍**；好处是标定过程变成了"改 4 个数字"，
而且改错会立刻在编译时被提醒，而不是把舵机顶死烧掉。

### 4.4 一键动作：把操作手的手速塞进代码

比赛要求操作手在几秒内完成"放下机械臂—张开机械爪—收臂"，
靠人按组合键根本来不及，于是做了一键序列：

- 车1：模式 1 下 `L1` 一键放下、`L2` 自定义序列2、`R1` 一键摆臂、`R2` 自定义序列1；
- 每个序列是"分步 + 等上一步到位 + 错峰延时 + 张爪"的状态机；
- **序列进行中按右摇杆 / □ / ○ 立即中止**（这一条是现场救命设计：
  舵机卡住时操作手能立刻接管，而不是等序列自己跑完）。

车1 时代最难的一次排障是"MG995 不受控制"——
最后发现是序列卡在中间某一步（等不到到位判据）导致后续输入被忽略。
于是加了调试全局变量 `g_servo_seq_id / g_servo_seq_step`，
并且在序列里对"任意手动输入"做中止判断。**看得到的调试量，比猜快十倍。**

### 4.5 封版

10 月 30 日，车1 打完最后一次补丁，测试 209 项全过，打上标签 `car1-finished`。
那天之后，主仓库的 `main` 分支就冻结在车1 的最终状态，
新车的所有工作转到 `car2` 分支去做。

## 5. 车2：少一个舵机，多一套灵魂

车2 的结构把"下面那段 SG90"省掉了，只剩 3 个舵机。
听起来是简化，实际上意味着**所有标定、所有序列、所有限位都要重做一遍**。
这一次我们决定把车1 时代零散的经验，做成一套"控律体系"。

### 5.1 三个舵机的新极限

重新标定后的关键数字：

| 通道 | 舵机 | 机械范围 | 安全窗口（脉宽） |
|---|---|---|---|
| CH1 | MG995（大臂） | 0° ~ 140° | 500 ~ 2050µs |
| CH4 | SG90（上臂） | 5° ~ 170° | — |
| CH3 | 机械爪 MG90S | 两端各留 5° → 行程 80° | 412 ~ 1300µs |

### 5.2 角度配置体系

把车1 的"4 个宏"升级成完整体系：

```c
#define SERVO0_OFFSET_DEG    (-10)   /* 电气零位 */
#define SERVO0_MIN_ANGLE_DEG   0     /* 机械下限 */
#define SERVO0_MAX_ANGLE_DEG 140     /* 机械上限 */
#define SERVO0_START_ANGLE_DEG 0     /* 上电姿态 */
```

`MIN_US / MAX_US / START_US` 由宏自动换算；顺带还有一个 `SERVO_STEP_FROM_DEG(°/s)`
把"速度"也变成宏，**改节拍时速度不会再莫名其妙地变**（这个坑在车1 时代踩过）。

### 5.3 角度斜坡

不管目标怎么跳变（摇杆、点动、一键序列），舵机都走 `slew_toward_target()`：

- 每 tick 用 0.1µs 的定点累加器向前推进，避免整数截断导致的"速度偏小"；
- 精确到位（最后一 tick 补齐余量），不抖、不超调。

### 5.4 加减速曲线，以及"9/9 的诞生"

只有恒定速度的话，舵机启动和停止像是"被踹了一脚"。于是加了加减速曲线：

- 起步：每个 tick 最多增加 `巡航速度 / ACCEL_DIV`，逐渐到巡航速度；
- 巡航：匀速；
- 收尾：剩余距离不足 `RAMP_TICKS` 个 tick 的行程时，按剩余距离线性降速；
- 末端最低速 = 巡航/4，防止最后几微秒爬得太久。

参数调了一整轮，现场反馈来来回回：

| 版本 | 起步 / 收尾 | 反馈 |
|---|---|---|
| 8 / 10 | 80ms / 100ms | "加速度不太明显" |
| 20 / 20 | 200ms / 200ms | "太缓和了" |
| 12 / 12 | 120ms / 120ms | "有点拖" |
| 8 / 6 | 80ms / 60ms | 收尾干脆，但… |
| **9 / 9** | **90ms / 90ms** | **"可以"** ← 最终定稿 |

这就是那个流传下来的注释：

```c
// 现场调参记录：8/10 加速度不明显；20/20 太缓和；12/12 有点拖；
// 8/6 收尾干脆 -> 现采用 9/9（起步/收尾各约 90ms，折中）。
#define SERVO_RAMP_TICKS       9
#define SERVO_RAMP_ACCEL_DIV   9
```

### 5.5 错峰：一个 tick 只做一件事

四个舵机同时动，电池和降压模块会瞬间"软脚"。所以加了**手动优先级**：

```
MG995（右摇杆） > SG90下（L1/L2） > SG90上（R1/R2） > 机械爪（□/○）
```

同一 tick 只有优先级最高的那一路能得到新的目标，其它输入被忽略（不是丢帧，是排队等下一 tick）。
一键序列内部则是"分步等到位"，天然错峰。

### 5.6 联动限位

机械结构上，大臂抬得太高会和上臂打架。于是加了一条软限位：

> **MG995 ≥ 138° 时，SG90(上) 不允许超过 87°。**

两个位置都生效：设置 CH4 目标时先按 MG995 当前角度限幅；每个 tick 再检查一次，
一旦 MG995 抬过 138°，CH4 的目标立刻被压回 87°。**MG995 本身不受反向限制**
（否则大臂会被卡死）——这是反复试出来的方向性。

### 5.7 机械爪：5° 的温柔，和"越近越慢"

机械爪是最容易烧钱的部件。车1 时代夹空物能一直顶到堵转发烫，于是车2 加了三层保护：

1. **两端各留 5° 安全余量**（`SERVO_GRIP_TRIM_DEG = 5`）：
   行程从 90° 收到 80°，脉宽 412~1300µs，一键合上停在 700µs；
2. **越靠近闭合端越慢**（`SERVO_GRIP_SLOW_*`）：
   进入最后 25° 线性降速，贴到闭合端只剩 20% 速度——"夹到手也不会太疼"；
3. **按住到位后断 PWM**（`SERVO_GRIP_RELEASE_MS`）：
   一直顶着限位不动，就干脆失力，避免长时间堵转。

### 5.8 一键放下 / 一键摆臂

车2 的按键重新分配（模式 0 = 上电默认）：

| 按键 | 动作 |
|---|---|
| `L1` | **一键放下**：MG995 →（跳过 CH2）→ SG90上 → 延时 → 张爪 |
| `L2` | **一键摆臂**：SG90上 → MG995 →（跳过 CH2）→ 延时 → 张爪 |
| `R1 / R2` | SG90(上) 点动（模式 0 下） |
| 右摇杆 Y | MG995 手动 |
| `□ / ○` | 机械爪张开 / 合上 |
| `SELECT` | 切换模式：模式 1 只剩机械爪一键张合 |

序列里"跳过 CH2"是自动的——`seq_step_channel()` 会检查 `SERVO_HAS_SG90_LOW`，
车2 编进去就没有这一步。**同一个序列代码，两辆车都能用**，这是移植时最省心的地方。

## 6. PS2 掉模式：一场和 200Hz 的战争

这是整个项目最像"玄学"的一段。

**现象**：手柄玩着玩着就从红灯（模拟模式）跳成绿灯（数字模式），摇杆全部失效，只能拔电重来。

**第一反应**：加自动恢复。检测到数字模式就重发配置序列把它拉回模拟模式。
一开始限速 500ms，后来发现恢复太慢。

**第二反应**：把恢复做得更狠——

1. 掉模式的**第一帧就立即重发配置**（无视限速），尽量缩短失控时间；
2. 之后按 200ms 限速重试；
3. 连续 3 次拉不回来 → 升级成整包 `PS2_Init()` 重新初始化（重识别型号 + 全量配置）。

写完这段之后 host 测试直接**栈溢出崩溃**（0xC00000FD）——
因为 `PS2_Init()` 内部还会读包，读包又检测到掉模式，又调用 `PS2_Init()`，无限递归。
加了一个 `s_reinit_guard` 防重入才稳住。
**这是回归测试第一次真正意义上"抓住"了一个致命 bug。**

**最终的根因**：还是把轮询改回 **10ms（100Hz）** 才彻底稳定。
廉价 2.4G 接收器根本吃不下 200Hz 的包流，它会自己退回数字模式"保命"。
同时把**振动功能关掉**（`PS2_ENABLE_RUMBLE = 0`）——项目从来没用过振动，
但那两条振动字节是写给接收器的额外负担。

> 结论：不是所有"更快"都更好。100Hz 是这颗手柄的舒适区。

## 7. 底盘：档位、软启动与 60 / 85

麦轮逆解的公式不复杂，难的是**手感**。最后的档位设计：

| 档位 | 切换 | 平移范围 | 满杆自转 | 满杆绕后轮 |
|---|---|---|---|---|
| 慢速 (0) | ✕ | 10% ~ 30% | 30% | 60% |
| **中速 (1)｜默认** | — | **30% ~ 60%** | 60% | 78% |
| 快速 (2) | △ | **60% ~ 85%** | 85% | 92% |

三点解释：

1. **档位首尾相接**（30 / 60 / 85），不再有"两档重叠"的模糊区；
2. **绕后轮单独映射到物理可用区间 600~920**：低于 600 那个轮子根本转不动，
   所以慢速档绕转是 60% 而不是 30%（2:1 差速的物理需要）；
3. 全局上限 **92%**（`CTRL_DUTY_CAP`）保留：再高实测会复位甚至打火。

另外两件事：

- **软启动 + 加减速曲线**：满载 385ms 爬到位，起步 80ms 渐加速、收尾 50ms 渐减速，
  `Motor_StopAll/BrakeAll` 会清零速度状态，下次起步从 0 开始；
- **失联保护**：3 秒没收到有效包就停车；上电时还要 4 轴回中持续 200ms 才允许使能（防上电乱跑）。

## 8. 那些坑（认真总结版）

| # | 坑 | 根因 | 结论 |
|---|---|---|---|
| 1 | 手柄"偶尔全 0" | 拿 buf[1] 和 0x5A 比 | 0x5A 在 buf[2]；整包重写 |
| 2 | 一推电机就复位 | 电源压降/接线松 | 先查电源再查代码；加猫须电容 |
| 3 | 无法烧录 | 工程目录改名后 `_build_flash/CMakeCache.txt` 还指向老路径 | 删构建目录重建；换个名字就"失忆" |
| 4 | 修改舵机速度后实际速度不对 | 改了 `PS2_READ_PERIOD_MS` 忘了同步 `SERVO_TICK_MS` | 速度用 `°/s` + 宏自动换算；三处必须联动 |
| 5 | 联动限位把序列卡死 | 序列目标角 158° 超过了限位 87° | 序列角度宏必须 ≤ 限位；测试按限位感知写 |
| 6 | 机械爪夹空物发烫 | 一直顶着限位堵转 | 5° 余量 + 近闭合减速 + 到位断 PWM |
| 7 | 栈溢出（host 测试崩溃） | 掉模式恢复调用 `PS2_Init()` 递归 | 加防重入守卫 |
| 8 | 手柄总掉模式 | 200Hz 轮询超出接收器能力 | 回到 10ms + 关振动 + 快恢复 |
| 9 | GitHub 传不上去 | 代理 TLS 中间人 → 证书签名失败 | `GIT_SSL_NO_VERIFY` + HTTP/1.1；后来网络抖动 → 部分克隆 |
| 10 | PowerShell 改中文文件乱码 | `Set-Content -Encoding UTF8` 加 BOM 并重写全文 | 中文文件只用编辑工具；`.ps1` 反过来**必须**有 BOM |

## 10. 工程之外：测试、文档、上云

**主机端回归测试**是这个项目最值的技术决定之一：

- 一个 `tests/host_test.c`，自带 HAL/外设打桩，`gcc` 直接编译成 Windows 可执行文件；
- 每次改参数、改逻辑，先跑一遍（1 秒内出结果），再决定要不要上车；
- 它抓到过：栈溢出递归、序列卡死、精确步长断言失效、机械爪跨度算错……

**文档**写了两份长文（PS2 排障 40KB、上电验证清单 33KB），以及一份持续追加的
`docs/更新日志.md`——后来上传脚本会自动把这份更新日志追加到团队仓库的 `Source_Code/log`。

**上云**折腾了很久：先是代理 TLS 中间人导致证书校验失败，改用
`GIT_SSL_NO_VERIFY=true` + HTTP/1.1 才推上去；后期网络时通时断，
于是把上传脚本从"整仓克隆"改成 **部分克隆 + 稀疏检出**（`--depth 1 --filter=blob:none`），
克隆时间从几分钟/经常失败变成 **2 秒级**，再配上内外两层重试，终于稳定。

## 11. 关于我们

项目仓库叫 `The_log_of_Zero_Reapers_Team`（零·死神小队）。
名字是别人起的，代码是我们一行一行敲的。

这个项目里没有天才式的顿悟，只有：

- 一次一次重标定的机械角；
- 一张一张手画的时序图；
- 深夜里"好像好一点了"的调参；
- 和"为什么它又复位了"的追问。

如果说有什么值得留下的经验，大概是这几条：

1. **改一个数之前，先想清楚它还牵动了谁**（节拍 → 速度 → 软启动，三处联动）；
2. **能用编译期宏解决的问题，不要留到现场调**；
3. **任何"偶尔"的现象都有确定的原因**，只是还没找到；
4. **写测试，它会替你在未来某天挡下一颗子弹**；
5. **先怀疑电源。**
